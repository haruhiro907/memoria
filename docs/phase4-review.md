## 2. 本レビューで修正したもの

1. **/explore に「おわり（ホームへ）」ボタンがなかった。**
   仕様 §2 の遷移一覧（「おわり」→ ホーム）と §8 が求める「3 大ボタン」に対し、実装は「まえ／つぎ（最後は最初からもう一度）」の 2 ボタン＋ AppShell の「ホームへ戻る」で代替していた。本人の画面としては仕様どおり画面内に大きな「おわり」を置くべきなので、ボタン列の下に quiet トーンの BigLink を追加した（自動遷移はしない）。

2. **joinFamilyWithCode の attempts の数え方が §1.3 とずれていた。**
   「使用済みコードの提示」が失敗としてコード側 attempts に数えられていなかった（期限切れの提示だけが数えられていた）。使用済みの提示でも attempts を +1 するよう修正。また「すでに家族に参加済み」のケースが「使用済みコード」と同じエラーに潰れていたため、状態を切り分けて `already-joined` を返すよう修正（クライアント側の文言は用意済みだった）。

3. **storage.rules のコメント誤字**（「使意する」「拒否化する」）を修正。ルール内容の変更なし。

4. **rules-test の追加**（scripts/rules-test.mjs、追加分 10 件・全 37 件）:
   - A8: createdAt をクライアント時刻で偽装した記録の拒否（serverTimestamp 強制の確認）。
   - E1〜E5: 本人ロールの編集拒否の残り（写真の更新・削除、links 作成、people の作成・更新・削除、events の削除）と、本人が写真を追加できること・他人の addedByUid を名乗れないことの確認。
   - F1〜F4: Storage の家族分離（自家族の読み書き可否、他家族・未ログインの拒否、本人の削除不可）。

## 3. 仕様からの意図的な差分（記録）

| # | 差分 | 理由と影響 |
| --- | --- | --- |
| D1 | inviteCodes ドキュメントに仕様 §1.3 の一覧外のフィールド（`code`・`personUid`・`displayName`）を持たせている | `code` は COLLECTION_GROUP 索引での照会に必須（コード文字列から発行元家族を特定する唯一の経路）。`displayName` は参加時に member へ引き継ぐため。`personUid` は参加先の「優先候補」の印としてだけ使い、参加可否を縛らない（縛ると §1.6 の「本人が自分で登録してから参加」フローが成立しない）。 |
| D2 | sendPersonPasswordReset はメール送信そのものをせず、「宛先が本人 member の登録メールと一致することの確認」までを Functions が行い、実際の送信はクライアント SDK の sendPasswordResetEmail が行う | §1.5 の画面上の振る舞い（本人のメール宛に再設定メールが届く）は同一。Admin SDK の generatePasswordResetLink は「リンクを家族へ渡す」形になり、仕様の想定（本人宛メール）とずれるため採らない。 |
| D3 | パスワード 8 文字以上を「推奨」ではなく Functions 側で必須にしている | 家族が弱いパスワードのまま発行してしまう事故を防ぐため。仕様の趣旨（家族が設定・保管する）とは矛盾しない。 |
| D4 | クライアントの recordPhotoViewed に同一（uid・写真・method）の 1.5 秒以内の重複送信を抑える窓がある | React StrictMode の二重マウント等による機械的な二重記録を吸収するため。仕様 §4.1 の「表示のたびに 1 件」と厳密にはずれるが、1.5 秒以内に同じ写真を同じ経路で再表示する操作は通常起こらず、分析への影響は無視できる範囲。窓の存在と理由はコード内コメントに明記。 |

## 4. 観察事項（仕様違反ではない）

- O1: /map では年精度の出来事が同年に複数ある場合「この年の出来事」クラスタにまとまる。年精度同士の前後はデータから定まらないため §3.1 の「古い順」と矛盾しないが、仕様に明記はない実装判断（ファイル冒頭コメントに記録あり）。
- O2: members の Rules は §6 の指定どおり Phase 3 のまま（家族ロールによるクライアント側の member 作成が Rules 上は可能）。本人の member 作成を Functions 経由だけに寄せるのは運用上の取り決めであり、Rules では強制していない。将来しめたい場合は Rules 変更が別途必要。
- O3: seed-dev.mjs の仮データ投入は Firestore への gRPC 接続を使うため、実行環境によっては接続制限で進まないことがある（開発用スクリプトの範囲）。
